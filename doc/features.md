# Preflight - 功能设计

Preflight 用于把可重复的工作固化为检查单模板，并为每一次执行保留独立、可追溯的执行记录。模板后续修改不会改变已创建 Run 中的步骤内容。

当前版本提供：

- Google 登录、多设备 session 与按用户隔离的数据访问；
- List Template 模板的新建、编辑、归档与版本保存；
- 仅文本 Checkbox 步骤，支持拖拽排序和可跳过标记；
- 从模板发起 Run，记录逐项结果、备注、开始和结束时间；
- 模板库、模板历史和全部执行历史的搜索与筛选。

数据库表、约束和索引 SQL 见 [database.md](database.md)。

## 1. 核心概念

| 概念              | 含义                                                          | 是否可变                                                   |
| ----------------- | ------------------------------------------------------------- | ---------------------------------------------------------- |
| Checklist         | 检查单模板，稳定身份和当前元数据。                            | 部分可变                                                   |
| Checklist Version | 检查单的执行模式与有序步骤的定义。                            | 仅在检查单进入草稿模式时，可以改变最新版本，其他情况不可变 |
| Run               | 用户基于模板最新版本发起的一次执行，持久化为 `run_instance`。 | 执行中可变，结束后冻结                                     |

```text
ListTemplate 1 -- * ListTemplateVersion
                         |
                         +-- steps jsonb
                         |
                         +-- RunInstance -- steps jsonb
```

步骤不作为独立实体，不拥有步骤 ID，也没有单独的新增、编辑、删除或排序接口。模板版本与 Run 都使用完整有序数组，因此模板编辑或归档后，历史 Run 仍保留当时的步骤内容和顺序。

## 2. 用户与权限

- 首页对未登录用户显示产品介绍和 Google 登录入口；受保护页面跳转至登录页。
- Google 登录是唯一身份提供方；一个 Google `sub` 对应一个 `account` 记录，存入 `google_id` 字段。
- 用户只能读取或修改自己的 List Template 和 Run。服务端必须从会话取得用户身份，不信任客户端提交的用户 ID 或审计字段。
- 用户名创建后不可变；同一用户名只对应一个用户。
- 同一账号可在多个设备登录；每台设备使用独立 session，退出单台设备只删除对应 session。

## 3. List Template 模板

### 元数据

| 字段             | 规则                                                                    |
| ---------------- | ----------------------------------------------------------------------- |
| `slug`           | 用户范围内唯一；用于 URL，名称变更不自动修改                            |
| `name`           | 必填，1-120 个字符                                                      |
| `description`    | 可选，最多 255 个字符                                                   |
| `category`       | 可选单个文本分类                                                        |
| `icon`           | 可选 Iconify 图标名                                                     |
| `archived_at`    | 非空表示归档；不可新建 Run，历史仍可查看                                |
| `execution_mode` | 执行模式；`0` 为 `free`，`1` 为 `sequential`，`2` 为 `strict`；默认 `0` |

模板元数据存入 `checklist`。编辑模板始终提交完整元数据和完整步骤数组；无论修改名称、描述、执行模式、步骤内容、跳过属性还是拖拽顺序，服务端都创建新的 List Template Version，并更新 `checklist.current_version` 与 `updated_at`。已有版本绝不原地更新。

### 文本步骤与拖拽排序

步骤只包含文本内容，不提供图片、文件或其他附件功能。`checklist_version.steps` 是 JSON 数组，每个元素包含：

| 字段           | 规则                                                     |
| -------------- | -------------------------------------------------------- |
| `content`      | 必填，1-200 个字符                                       |
| `description`  | 可选，最多 255 个字符；Markdown 以纯文本存储，渲染时消毒 |
| `group_name`   | 可选，仅用于视觉分组，不影响完成逻辑                     |
| `is_skippable` | 默认 `true`；决定自由和顺序模式下能否跳过                |

数组元素顺序就是显示顺序和创建 Run 时的顺序。编辑器支持拖拽排序，但保存只提交完整步骤数组，不会单独更新任一步骤。保存时校验数组非空与元素字段有效性。

## 4. Run 状态与执行规则

### Run 状态

```text
0 not_started -- start --> 1 in_progress -- complete --> 2 completed
      |                         |
      +-------- cancel --------+-- cancel -------> 3 cancelled
```

点击“开始执行”时创建 `status = 1` 的 `run_instance` 并设置 `started_at`。创建 Run 的事务读取最新模板版本的完整步骤数组，直接写入 `run_instance.steps`。Run 快照数组顺序固定，历史展示和顺序执行都按数组位置进行。结束时设置 `finished_at`；耗时由 `finished_at - started_at` 计算，不持久化。

Run 步骤快照是模板步骤的扩展，新增以下执行字段：

- `checked = true`：成功；
- `checked = false`：失败；
- `checked = null` 且 `resolved_at` 非空：跳过；
- `checked = null` 且 `resolved_at` 为空：未处理；
- `skip_reason`：仅跳过时可选填写。

处理成功、失败或跳过时写入 `resolved_at`；恢复为未处理时清空执行字段。仅 `status = 1` 的 Run 可更新。

### 执行模式

- 自由模式可按任意数组位置处理步骤；允许成功、失败，且 `is_skippable = true` 的步骤可跳过。处理后不自动定位下一步骤。
- 顺序模式只能处理第一个未处理步骤。成功、失败或跳过后自动定位下一步骤；仅 `is_skippable = true` 的步骤可跳过，跳过原因可选。
- 严格模式同样按顺序自动定位下一步骤，但不允许跳过。无法执行时标记 `checked = false` 后进入下一步骤。

完成条件为所有步骤都已处理，且没有违反执行模式的结果。失败是已处理结果，不阻止完成。服务端在结果变更与完成请求时校验。

`run_instance.meta` 保存运行期附加信息，例如用户授权后的地理位置。

## 5. 页面与交互

所有登录用户相关页面均位于 `(app)` 路由分组下，服务端根据 cookie 中保存的 session 认定用户信息。

| 路由                   | 目的              | 主要内容                                       |
| ---------------------- | ----------------- | ---------------------------------------------- |
| `/`                    | 首页              | 未登录时显示介绍和登录；登录后跳转至用户模板库 |
| `/list`                | 模板库            | 活跃模板、搜索、分类筛选、新建模板             |
| `/list/new`            | 新建模板          | 元数据、模式、可拖拽步骤编辑器                 |
| `/list/[slug]`         | 模板详情          | 当前版本步骤、最近 Run、开始执行、编辑、归档   |
| `/list/[slug]/edit`    | 编辑模板          | 当前版本完整副本；保存总是创建新版本           |
| `/list/[slug]/history` | 模板历史          | 按开始时间倒序，状态、日期和关键词筛选         |
| `/run/[id]`            | 执行页和 Run 详情 | 进行中时更新步骤结果、取消、完成；结束后只读   |
| `/run`                 | 全部历史          | 当前用户所有 Run，支持模板、状态和日期筛选     |

关键交互：

1. 开始执行立即创建新 Run 并进入对应执行页；重复点击不会复用旧 Run。
2. 标记成功、失败或跳过均立即保存；失败时保留本地输入并允许重试。
3. 完成前显示未处理步骤数量；只有服务端校验通过才能完成。
4. 取消需要二次确认，并保留已经处理的 Run 快照与 `meta`。
5. 历史项显示开始日期、状态、耗时、成功/失败/跳过数和模板版本；详情显示“基于模板 vN”。

## 6. 服务端边界

SvelteKit 页面使用 server load/actions，不为页面重复建设 REST 层。

模板更新请求必须包含完整步骤数组；不存在步骤独立 CRUD 接口。Run 步骤的 `position` 从 1 开始，映射到创建后固定的快照数组位置。列表使用游标分页，默认按 `started_at DESC`。所有写操作从会话取得用户 ID；“保存模板版本”、“创建 Run + 复制步骤”、“更新步骤结果 + 校验顺序”和“结束 Run + 校验完成条件”必须在一个事务中完成。

## 7. 审计、隐私与安全

- 自动记录开始/结束时间和执行人。地理位置等运行期附加信息在用户授权后写入 `run_instance.meta`，缺失时保持 `NULL`。
- Markdown 仅使用受信任的消毒渲染器输出，禁止原样插入 HTML。
- 完成或取消后的 Run 及其步骤快照不可更新；归档模板不删除历史。

## 8. 验收标准

1. 创建包含可跳过步骤的模板，版本步骤数组正确显示。
2. 拖拽排序后完整保存步骤数组，数组顺序正确；旧版本 JSON 不变。
3. 修改任意模板元数据或步骤都会创建 v2；不存在步骤单独更新。
4. 以 v1 创建 Run 后，Run 快照按创建时数组顺序显示，不受 v2 影响。
5. 自由模式允许任意顺序处理，且不会自动定位下一步骤。
6. 顺序模式自动定位下一步骤，并允许跳过 `is_skippable` 步骤及可选填写跳过原因。
7. 严格模式只允许按顺序处理，不允许跳过；失败后自动进入下一步骤。
8. `checked = true`、`false`、`null` 分别正确记录成功、失败、跳过；`resolved_at` 能区分跳过和未处理。
9. 已完成或取消的 Run 无法再通过服务端更新 JSON 步骤快照或状态。
10. 用户 A 无法读取、编辑、开始或更新用户 B 的 List Template 和 Run。
11. 历史列表能按状态、日期和关键词筛选，并显示正确耗时与模板版本。

## 9. 实施顺序

1. 建立 PostgreSQL 适配器、迁移与用户会话边界。验证：迁移可重复执行，用户隔离测试通过。
2. 实现 List Template、完整版本保存和可拖拽步骤编辑。验证：每次保存创建新版本，旧 JSON 不变。
3. 实现 Run JSON 快照、状态机和执行页。验证：快照独立、位置更新、顺序限制和完成条件通过。
4. 实现模板库、历史和搜索筛选。验证：用户隔离和历史筛选通过。

当前代码仍有 MongoDB 风格的 `db.templates` / `ObjectId` 调用；实现第 1 步时应以 PostgreSQL 适配器替换这些 Checklist 读取路径，而不是在同一业务流中维护两套数据源。
